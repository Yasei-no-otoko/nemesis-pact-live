# GPT-Live-1 導入評価 — 2026年9月13日確認

## 結論

**採用価値はある。ただしv0.5.0に音声接続は含まれていない。最優先はテキスト版の実モデル交渉を成立させ、その同じ契約経路に音声を追加すること。**

GPT-Live-1を「存在未確認」「まだAPI非公開」と扱うのは誤りです。OpenAIは9月10日の公式発表でAPI提供を告知しています。[1][2] 一方、APIの提供開始と、この参加者のプロジェクトから利用できること、個別実装で接続・動作することは別の確認事項です。

## 一次ソースから確認できたこと

GPT-Live-1は聴取と発話を同時に行う全二重の音声フロントエンドです。深い推論やアクションをバックエンドモデル・エージェントへ委譲します。[1] OpenAIの公式コミュニティ告知では、ブラウザ向けWebRTC、サーバー向けWebSocket、電話接続、managed Responses delegationまたはclient delegationが説明されています。[2]

料金はフロントエンド音声層が **0.05米ドル/分**。秒単位の課金で、バックエンドモデルとツールの利用料は別です。[1][2] 例えば1人90秒、100人なら合計150分となり、音声層のみ **7.50米ドル**。接続維持時間・バックエンド呼び出し・再試行等を含む総額の保証ではなく、単純な利用時間の試算です。

音声への割り込みとバックエンド処理のキャンセルは別であり、アプリが権限と状態を管理する必要があります。[2] 公開記事のCodex接続例も、接続初期化とdelegation処理を省略した抜粋です。[1] そのコードだけからブラウザ用ハンドシェイクや完全なイベント仕様を推測して実装済みとは扱えません。

## NEMESIS PACTへの採用案（設計。未実装）

プレイヤーが「左ではなく右を安全にして。増援は構わない」と話す。Notaryは条件を確認しながら聞き続ける。バックエンドのテキストモデルが `living-covenant-v1` の候補を返す。ゲーム側がスキーマと予算を検証し、正規化した条項を表示する。**物理的なSignボタンの操作**で初めて戦闘へ反映する。

```text
Browser microphone / explicit opt-in
        │ WebRTC (future transport)
        ▼
GPT-Live-1 — speech interaction
        │ delegation (validated protocol required)
        ▼
Text reasoning backend → bounded covenant proposal
        │ server + client validation
        ▼
Canonical benefit / price display → explicit signature → simulation
```

v0.5.0で実装したのは、この図のテキスト要求以降のルール／署名経路とサーバーアダプターです。`/api/covenant` の `OPENAI_MODEL` はResponses用のテキストモデルです。`gpt-live-1` をそこへ入れるだけでは音声化できないため、設定エラーとして拒否します。

初回は初期契約画面と、戦闘を停止した再交渉画面だけで音声を有効にするのが適切です。常時マイクを戦闘BGMにさらすより、意図が明確になり、会場の騒音や切断でプレイ不能になるリスクを限定できます。テキスト入力と例文ボタンは残します。戦闘の移動・当たり判定・弾幕発射をLLMの応答待ちにしません。

## 実装着手時の確認ゲート

1. 参加者用プロジェクトのモデルアクセス、公式Live SDK/APIのブラウザ用セッション作成仕様、短命認証情報の発行方法を確認する。Realtime APIのモデル名置換で代用しない。
2. マイク許可を明示的に取得し、接続中表示、ミュート、終了、再接続、端末／タブ離脱時のクリーンアップを実装する。現在のCSP・Permissions-Policyは音声接続を許可していないので、接続先を絞ったHosted専用の変更が必要。
3. 契約revision、run/session ID、request IDをdelegationに関連付ける。「右へ変更」「今のは撤回」という発話、割り込み、遅延返信、重複返信で旧条件が署名されないことをテストする。
4. モデルの口頭説明を機械的権限にしない。条項の表示と読み上げが不一致の場合は表示を正とし、候補を再確認させる。口頭の「はい」だけで不可逆に署名しない。
5. 1セッションの時間上限、会話中でない時の切断、共有の永続クォータ、推論費用と音声費用の両方を管理する。
6. 実端末・会場に近い雑音・ヘッドセット／スピーカー・日本語で検証し、失敗時は即座にテキストへ戻す。実測遅延・成功率を記録する。

## 締切までの優先順位

P0: 実モデルのテキスト要求→契約→戦闘変化を検証・録画する。P0: 1分動画URLとアクセス可能な提出物を確定する。P1: 上記ゲートを通過できた場合に限り音声交渉を追加する。P2: 常時実況・挑発・多人数音声などは今回の必須要件から外す。

未実接続のGPT-Liveを動画や応募文で稼働中と表現しないことが重要です。全二重音声は独自性を増す可能性がありますが、同じ文章を読むだけではゲーム性への寄与は弱いので、**プレイヤーの言い直しが契約条件を変える場面**を短く見せる構成を推奨します。
